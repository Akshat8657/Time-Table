## 4. College Structure

- A college has **Schools** (departments). Examples: School of IT, School of Business, School of Law.
- Current focus: **School of IT**. The same logic must work for every school added later.
- School of IT has these courses:
  - **B.Sc. IT** — Sem 1 to Sem 7
  - **M.Sc. IT** — Sem 1 to Sem 3
  - **M.Sc. AI** — Sem 1 to Sem 3
- A "class" = course + semester (example: B.Sc. IT Sem 3). Keep the data model ready for divisions (Sem 3 - A, Sem 3 - B) later.
- **Odd / Even term system**: at any time the college runs ONLY odd semesters or ONLY even semesters.
  - **Odd term** (starts around July): Sem 1, 3, 5, 7 run — the new batch starts Sem 1, old batches move to Sem 3, 5, 7.
  - **Even term** (starts around January): Sem 2, 4, 6 run.
  - Admin/HOD selects the **active term** (odd or even + year, e.g. "Odd 2026"). Timetables are made ONLY for the active term's semesters. Old terms stay saved as history.
- Faculty belong to ONE school only and teach only inside that school.
- **HOD is also a teacher** — HOD takes lectures too.
- **Rooms are NOT managed by this software.** Every class already has its fixed room in the college. No rooms data, no room screens, no room rules — anywhere. Never add room features.

## 7. Timing System

- Admin sets college hours (example 10:00–17:00).
- Lecture duration is configurable (default **1 hour**) + a **short break (default 5 min) after every lecture**.
- The system auto-builds the daily period grid from these settings.
- **Lunch break timing can be DIFFERENT per school** — HOD sets his school's lunch (admin can override).
- **Semester-wise early release**: some semesters end early (e.g. 3:00 PM), others run full day (5:00 PM). Set per semester. The generator must NEVER place a lecture after that semester's end time.
- Working days are a setting in Timing Setup (Mon–Fri or Mon–Sat), changeable anytime.

## 8. Subjects, Credits, Labs, PE & SOL

- Every subject has: name, code, **credits**, type (Core / Elective), lab flag, total **semester hours**.
- **Credits = minimum lectures per week.** Example: 4 credits → at least 4 lectures every week.
- **Semester hours must be fulfilled** by semester end, even when holidays come (Section 12).
- **Labs**: a lab session is always **2 back-to-back lectures** (one continuous block). The generator must place lab blocks, never a single lab period.
- **PE (Physical Education) and SOL (Science of Living)**:
  - Compulsory for **ALL classes of ALL courses**.
  - **Always back-to-back 2 lectures** (double block), exactly like labs.
  - Their weekly slots are **manually fixed** by HOD/Admin on the Fixed Slots screen.
  - The generator treats them as LOCKED and schedules everything else around them.
  - **Credits do NOT decide PE/SOL lectures.** Whatever their credits (even 1), every PE/SOL session on the timetable is ALWAYS a double block counted as **2 lectures (2 hours, back-to-back)**. Their weekly lecture count comes ONLY from the manually fixed slots, never from credits. The "credits = minimum weekly lectures" rule does not apply to PE and SOL.

## 9. Electives (Specialization Subjects)

- Almost every semester has some **elective subjects** — students of the same class choose different ones. (No student login — the system only manages subjects, teachers, and slots.)
- HOD marks a subject as **Elective** and puts the electives of one semester into an **Elective Group**. Example: B.Sc. IT Sem 5 → Elective Group A = { AI, Cyber Security, Data Science }.
- Each elective has its **own teacher**, assigned like any normal subject.
- **Scheduling rule: ALL electives of one group run in the SAME time slots (parallel).** Students split by their choice, and every student is busy at the same time — so a student clash is impossible.
- All electives in one group should have the **same credits** (= same weekly slots). If credits differ, show a warning to the HOD during setup.
- Clash check: EVERY elective teacher of the group must be free in those common slots.
- Timetable cell display: "Elective: AI / Cyber / DS (parallel)" with teacher names.
- Substitution: if one elective teacher is absent, only that one elective is affected — normal substitution flow (Section 13).

## 10. Scheduling Rules (the engine's brain)

### Hard rules — NEVER break
1. One teacher can be at only one place at one time.
2. One class has only one lecture at one time (an elective group's parallel slot counts as one combined lecture).
3. A teacher teaches only the subjects assigned to them.
4. Labs and PE/SOL = continuous double blocks, always.
5. Fixed slots are locked — the generator never moves them.
6. Visiting faculty only on their allowed days and within their allowed weekly hours.
7. A teacher's ❌ (not available) slots are never used.
8. No lecture after a semester's early-release time.
9. No lecture during that school's lunch break.
10. Weekly lectures of each subject ≥ its credits — EXCEPT PE and SOL: their lecture count comes only from their fixed double blocks (see Section 8), never from credits.
11. A teacher's max-lectures-per-day / per-week limits (set by HOD/Admin) are never crossed.

### Soft rules — try best (each has a weight 0–100%, set by Admin/HOD)
- ⭐ Teacher preferred slots (including "first lecture" / "avoid last lecture" choices).
- Same subject not twice in one day (labs excluded).
- Avoid long empty gaps for a class and for a teacher.
- Balance workload fairly across teachers.
- Spread each subject across the week.

### Generator behavior
- Tries many combinations, gives every draft a score based on soft-rule satisfaction, and shows the top 2–3 drafts with scores.
- If a timetable is impossible, it must clearly say WHICH rule is blocking (example: "Maths needs 4 slots but only 2 free slots remain for Sem 3").
- Manual drag-drop editing is always available, with real-time clash warnings.
- **Semi-automatic mode**: lock any slots by hand first (not just PE/SOL — anything); the generator fills everything else around the locked slots.

## 11. Timetable Generation Flow (what Admin/HOD does)

1. Select the **active term**: odd (Sem 1, 3, 5, 7) or even (Sem 2, 4, 6) + year. Only these semesters get scheduled.
2. Teacher accounts ready (select teachers of the school).
3. Set subjects + credits + semester hours (+ mark labs, electives, elective groups).
4. Assign: which teacher teaches which subject in which class.
5. Set timing (lunch, early release) + fixed slots (PE/SOL double blocks).
6. Press **Generate** → backend calculates everything → 2–3 drafts → compare → pick one → manual adjust if needed → **Publish**.
7. On publish: all affected teachers get notifications; PDF/Excel export is ready.

Shortcut: the previous semester's timetable can be **copied as a starting base** and then adjusted.

## 12. Holidays, Events & Semester Hours

- Admin manages **college-wide holidays**: preload a standard India bank-holiday list for the year, admin can add/remove any holiday.
- HOD can add **school-level holidays and events**. An event can block a full day or specific slots for selected classes.
- Each semester has a **start date + end date** (set in setup).
- The system calculates the real deliverable lectures per subject: weekly timetable × weeks − holidays − events.
- It compares this with the required semester hours. If any subject falls short → **red alert on dashboard** (example: "DBMS — 4 hours short").
- One click → the system suggests **clash-free extra slots** for compensation → HOD approves → done.
- This tracking runs LIVE for the whole semester. No subject should silently fall behind.

## 13. Absence & Substitution Flow

1. A teacher marks self absent (or HOD marks them, or the AI does it after a Confirm).
2. Instant notifications go out (HOD/Admin + affected people). The day's affected lectures are listed.
3. For each affected lecture, the backend ranks free teachers by: (a) can teach that subject / matching specialization, (b) free in that slot, (c) lower workload today, (d) has taught that class before.
4. Two modes:
   - **Manual**: HOD picks from the ranked list → that teacher gets a notification.
   - **Auto popup offer**: the top 3–5 free teachers get an offer popup ("Period 3 • B.Sc. IT Sem 3 • Maths — Accept?"). **First to accept wins**; the others see "already filled".
5. On accept: that day's timetable updates live, a substitution sheet entry is made, and the monthly summary counts it.
6. If nobody accepts within X minutes (configurable) → alert the HOD → manual assign.
7. Daily substitution sheet + monthly absence/substitution summary are always available.
8. **One-day adjustments**: HOD can move / cancel / swap any single lecture for a specific date, with live clash checks. The weekly base timetable stays unchanged.
9. **Smart suggestions**: the system suggests helpful moves, e.g. "this lecture can shift earlier today — teacher and class are both free".

## 14. Teacher Preferences

- Weekly grid per teacher: every slot = ✅ Available / ⭐ Preferred / ❌ Not available.
- Special choices: prefer **first lecture**, avoid **last lecture**, max lectures per day.
- Admin/HOD sets a limit on how many ❌ a teacher may mark (so nobody misuses it).
- **Visiting faculty**: allowed days (example: only Mon/Tue/Wed) + max weekly hours. These are HARD rules.
- HOD opens a "preference window" → all teachers get notified → they fill before the deadline.

### Commands it MUST handle (examples)

- **"Me aaj absent hu"** (any role: teacher/HOD/admin) → Confirm → marks that person's own absence → then automatically shows **today's free teachers**.

- "Period 3 me kon free hai?" → the same list, filtered for that period.
- "[Teacher name] ki details do" → name, specialization, subjects they teach, today's schedule.
- "B.Sc. IT Sem 3 ka Friday dikhao" → that timetable.

## 21. Security & Performance Standards (every phase, always)

- Every backend API checks the JWT + the role. Frontend route guards too.
- RLS policies on every table (user → own data; HOD → own school; admin → all).
- Passwords only via Supabase Auth; forced change on first login; rate-limit the login.
- **Login sessions**: secure session handling via Supabase Auth. Sessions auto-expire after inactivity (configurable, default 8 hours). "Remember me" option on the login page keeps the session longer on that device. Logout clears the session fully.
- **Cookies (with consent)**: on first visit, show a simple cookie-consent banner (Accept / Decline). If accepted → store only small conveniences: theme, remembered email on the login screen, last opened view. If declined → the site must still work 100%, store nothing extra. The login session itself is essential and always works. NEVER store passwords or personal data in cookies.
- Input validation everywhere. No secrets in code. CORS locked to localhost.
- Audit log for every important change: who, what, when, via UI or "via AI".
- Fast responses, efficient queries from day one (full load testing happens in Phase 8).
- Polished, simple, professional UI at every step.
